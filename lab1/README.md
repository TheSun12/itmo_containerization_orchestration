## Часть 2 - namespaces
Исправляя эту вседозволенность, я начала вводить ограничения для сервиса. 

Сначала необходимо поместить процессы в свои namespaces через `unshare`. Namespaces, которые я использовала:
- pid - свой список процессов и нумерация
- mount - своя файловая система и корень
- net - свой сетевой стек
- uts - свое имя хоста
- ipc - своя очередь сообщений
- user - свой маппинг пользователей

И на этом моменте была получена первая ошибка

![Ошибка при запуске unshare](/lab1/screenshots/image3.png)

На форумах я нашла информацию, что Ubuntu 23.10+ ограничивает использование пользовательских пространств имён непривилегированными пользователями с помощью AppArmor. Убрать это ограничение можно с помощью команды 

```bash
sudo sysctl -w kernel.apparmor_restrict_unprivileged_userns=0
```

После этого все заработало

![Добавление namespaces](/lab1/screenshots/image4.png)

Проверим хостовые ограничения, для этого посмотрим имя хоста через `hostname`. Для наглядности я изменила хостовое имя внутри процесса, чтобы было наглядно видно изоляцию хоста.

## Часть 3 - cgroups

Теперь нужно завести группу для процесса и навесить на эту группу лимиты.

Я создала группу `lab1docker`, включила контроллеры и добавила процесс в группу.

```bash
sudo mkdir /sys/fs/cgroup/lab1docker
echo "+memory +cpu +pids" | sudo tee /sys/fs/cgroup/cgroup.subtree_control
echo 5286 | sudo tee /sys/fs/cgroup/lab1docker/cgroup.procs
```

После этого я задала ограничения:
- ограничения по памяти - 50 Мб
- лимит на CPU - 50% ядра
- лимит на количество процессов - 10

```bash
echo 50M | sudo tee /sys/fs/cgroup/lab1docker/memory.max
echo "100000 50000" | sudo tee /sys/fs/cgroup/lab1docker/cpu.max
echo 10 | sudo tee /sys/fs/cgroup/lab1docker/pids.max
```

Проверим работу ограничений.

Я попробовала вызвать сервис через `curl`, но возникла ошибка.

![Ошибка при curl](/lab1/screenshots/image9.png)

Ошибка возникла из-за того, что я в предыдущем шаге изолировала сеть процесса. Сейчас у процесса пустая сеть, которая не дает получить доступ к себе снаружи. Чтобы это исправить я подняла lo.

```bash
sudo nsenter -t 5286 -n ip link set lo up
```

Теперь можно полноценно проверять работу ограничений.

Я запросила 10000 Мб памяти через эндпоинт `/eat`. Процесс убился. Я проверила, какие события были с памятью, и увидела, что смогла поймать OOM_Kill.

![Пойманный OOMKill](/lab1/screenshots/image10.png)

Дальше через эндпоинт `/burn` я нагрузила одно ядро. При просмотре статистики я увидела, что смогла поймать throttling - автоматическое ограничение производительности процессора.

![Пойманный throttling](/lab1/screenshots/image11.png)

Осталась проверка на число процессов. Я этого я воспользовалась `stress-ng` и запустила 50 процессов.

```bash
sudo bash -c '
    echo $$ > /sys/fs/cgroup/lab1docker/cgroup.procs
    cat /proc/$$/cgroup
    exec stress-ng --fork 50 --timeout 20s
'
```

При проверке статистики видно, что сервис не смог превысить ограничение в 10 процессов.

![Пойманные ограничения на число процессов](/lab1/screenshots/image12.png)

Следовательно, можно сказать, что все ограничения применились и успешно прошли проверки.

## Часть 4 - права

Проведем ограничение прав.

В первую очередь ограничим лишние capabilites. 

Проверем, какие права сейчас доступны процессу через `proc`. У моего процесса нет наследуемых (CapInh) и наружных прав (CapAmb), но есть все остальные. С помощью `decode` я посмотрела, что означают эти числа, и оказалось, что это практически все capabilities.

![Изначальные права](/lab1/screenshots/image13.png)

Чтобы ограничить права я использовала следующую команду.

```bash
sudo setpriv --bounding-set=-all --inh-caps=-all --ambient-caps=-all /home/taisiya/lab1/venv/bin/python3 api.py 
```

Теперь при проверке через `proc` все права по нулям.

![Ограниченные capabilities](/lab1/screenshots/image14.png)

Далее нужно навесить seccomp-профиль. Для написания фильтр я решила использовать Python и установила необходимые пакеты: `libseccomp-dev` и `pyseccomp` (обертка для работы с seccomp в Python). Написанный профиль находится в файле [seccomp-filter.py](/lab1/seccomp-filter.py).

При проверке видно, что фильтры успешно применились.

![Проверка seccomp](/lab1/screenshots/image15.png)

## Часть 5 - Собери свой Docker

Я собрала все наработки из 2-4 частей в один скрипт [mydocker.sh](/lab1/mydocker.sh) и запустила его.

Тут, если честно, при первом запуске у меня слетели все настройки root и даже sudo не работал. 

![Страсти со слетевшим root](/lab1/screenshots/image16.png)

После восстановления root-прав через GROUP стала изучать скрипт. Оказалось, что ларчик просто открывался, и я опечаталась, написав `group` вместо `cgroup`. Вроде маленький косяк, но вышел хороший урок о том, что нужно внимательнее проверять, что пишу :)

После исправления опечатки скрипт корректно заработал и запустил сервис. В эндпоинте `/health` приходил ответ `ok`.

![Проверка работы сервиса](/lab1/screenshots/image17.png)

После этого я запустила тот же сервис, но уже через `docker run`.

```bash
sudo docker run --rm --name api-docker \
    --memory=50m \
    --cpus=0.5 \
    --pids-limit=5 \
    --cap-drop=ALL --security-opt no-new-privileges \
    -p 5000:5000 \
    -v "$PWD":/api:ro \
    -w /api \
    python:3.14.7-slim \
    sh -c 'pip install --no-cache-dir flask && python3 api.py'
```

Сервис успешно запустился.

Сравнение скрипта и docker run:

| |Скрипт|docker run|
|-|------|----------|
|namespaces|записывали вручную через `unshare`|автоматическая настройка|
|cgroups|создавала через /sys/fs/cgroups/ с ручным добавлением процесса в группу|автоматически через заданные ограничения `--memory` `--cpus` `--pids-limit`|
|capabilities|настраивала через `setpriv`|настройка через `--cap-drop`|
|сетевые настройки|получалась пустая сеть, было необходимо настраивать дополнительно|своя сеть с заданным портом 5000:5000|
|seccomp|настройка через обертку `seccomp-filter.py`|свой профиль по умолчанию, но можно добавить свое|
|файловая система|от хоста напрямую|свой образ и слои|

Если выделять самые главные различия, то, на мой взгляд, более легкая настройка при docker run, позволяющая не создавать все настройки вручную, и своя собственная файловая система у docker.

## Часть 6 - Образы

Я написала [Dockerfile](/lab1/Dockerfile) и запустила его сборку.

```bash
sudo docker build -t myapi-single .
``` 

Потом написала [Dockerfile.multistage](/lab1/Dockerfile.multistage) и снова запустила сборку.

```bash
sudo docker build -f Dockerfile.multistage -t myapi-multistage .
```

Через команду `sudo docker images` я увидела, что все образы создались и находятся в общем списке. При этом multistage-сборка весит меньше, чем обычная. Это связано с тем, что в multistage-сборке нет кэша pip и временных файлов.

![Проверка образов](/lab1/screenshots/image19.png)

Сравним количество слоев через команду `docker history`. В обычной сборке 8 слоев, а в multistage - 7 (я считала только ненулевые слои, т.к. слои с 0B - метаданные). У multistage нет слоя `COPY requirements.txt` - он остался в builder и не попал в финальный образ. Слой `pip install` (16.9 МБ) заменён на `COPY --from=builder` (6.12 МБ) - потому что во втором случае копируется только результат (/root/.local/), без pip-кэша и временных файлов.

![Проверка слоев](/lab1/screenshots/image27.png)

При повторной сборке (после добавления комментария в api) я посмотрела, что бралось из кэша, а что пересобиралось. Видно, что довольно много слоев Docker брал из кэша, т.к. они не менялись с предыдущей сборки.

![Проверка кэширования](/lab1/screenshots/image20.png)
![Проверка кэширования](/lab1/screenshots/image21.png)

Дальше я проверила, что будет, если записать файл в контейнер без тома и с томом.

Протестируем создание файла в контейнере без тома.  
Сначала я создала файл и проверила, что он находится в app.

```bash
sudo docker run -d --name test1 myapi-multistage

sudo docker exec test1 touch /app/data.txt
sudo docker exec test1 ls /app/

>> api.py data.txt
```

При перезапуске контейнера файл не сохранился.

```bash
sudo docker rm -f test1
sudo docker run -d --name test1 myapi-multistage
sudo docker exec test1 ls /app/

>> api.py
```

Как видно, файл data.txt удалился вместе с контейнером.

Теперь проверим то же самое, но с томом. Сначала запустим контейнер и создадим в нем файл, а потом перезапустим и проверим, остался ли он

```bash
sudo docker volume create mydata

sudo docker run -d --name test2 -v mydata:/app/data myapi-multistage

sudo docker exec test2 touch /app/data/data.txt
sudo docker exec test2 ls /app/data

>> data.txt

sudo docker rm -f test2
sudo docker run -d --name test2 -v mydata:/app/data myapi-multistage
sudo docker exec test2 ls /app/data

>> data.txt
```

В этот раз файл сохранился и виден при перезапуске контейнера. Такая разница в работе объясняется эфемерностью записываемого слоя. Без контейнера файл был записан в верхний слой, который удаляется вместе с контейнером. А с томом файл сохранился в отдельное хранилище, поэтому остался нетронутым.

## Часть 7 - Когда контейнера мало

Перейдем на другой уровень и разберемся в gVisor. 

gVisor - технология "песочницы", обеспечивающая изолированный запуск контейнеров. gVisor помещает процессы в песочницу, перехватывая все системные вызовы от них к ядру хоста и обрабатывая их с помощью своего хоста (поэтому он и считается более изолированным).

После скачивания пакета gVisor я настроила конфигурацию в `/etc/docker/daemon.json`. После этого перезагрузила Docker.

```json
{
  "runtimes": {
    "runsc": {
      "path": "/usr/bin/runsc"
    }
  }
}
```

Для того, чтобы запустить образ под gVisor, я использовала эту команду.

```bash
sudo docker run --rm --runtime=runsc --network=host --name api-gvisor myapi-multistage
```

Чтобы проверить используемое ядро, я использовала команду `uname -a` как для gVisor, так и для хоста. Видно, что у gVisor написано ядро, которого на самом деле нет. Следовательно, он использует свое собственное ядро для изоляции процесса.

![Проверка ядра](/lab1/screenshots/image22.png)

В любом случае, у обычного контейнера остается общим с хостом аппаратные ресурсы, физическая память и хостовое ядро. Контейнерная изоляция может ограничивать видимость, но не может ограничить от уязвимостей хоста, т.к. сам контейнер - процесс на хосте, делящий то же ядро. Если хочется полной изоляции, тогда нужно использовать виртуальную машину.
